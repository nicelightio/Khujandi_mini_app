# Рекомендации по фронтенду для Telegram Mini App на React + TypeScript

## Назначение

Задача фронтенда в Telegram Mini App — не просто сделать красивый интерфейс, а добиться сочетания четырех качеств одновременно:

* современный визуал;
* плавность и отзывчивость;
* низкая нагрузка на мобильные устройства;
* стабильная работа внутри Telegram WebView.

Главный принцип: визуальная выразительность должна достигаться в первую очередь дешевыми по ресурсам приемами, а не тяжелыми библиотеками и эффектами.

---

## Ключевые приоритеты

При проектировании и разработке приоритеты должны идти в таком порядке:

1. отзывчивость и плавность;
2. стабильность в Telegram WebView;
3. быстрый первый рендер и быстрая загрузка;
4. аккуратный современный визуал;
5. анимации и эффекты только там, где они реально улучшают UX.

---

## Базовый профиль фронтенда

Фронтенд должен уверенно закрывать следующие области.

### React + TypeScript

* production-уровень React + TypeScript;
* компонентный дизайн;
* controlled и uncontrolled patterns;
* работа с локальным и серверным state без лишних re-render;
* маршрутизация и code splitting;
* mobile-first подход.

### Стилизация

* Tailwind CSS или CSS Modules / vanilla-extract;
* design tokens;
* CSS variables;
* theme adaptation;
* safe area и viewport handling;
* построение визуальной системы без тяжелого runtime CSS-in-JS.

### Анимации

* CSS transitions и keyframes;
* Web Animations API;
* Motion для React, но экономно и точечно;
* понимание, когда библиотека не нужна и достаточно CSS.

### Performance

* profiling re-renders;
* memoization только там, где есть смысл;
* virtualization;
* lazy loading;
* контроль bundle size;
* борьба с layout thrashing;
* transform/opacity-first анимации;
* контроль количества одновременно анимируемых элементов.

### Telegram Mini App-специфика

* theme vars Telegram;
* safe area Telegram;
* viewport и keyboard behavior;
* fixed bottom UI без багов;
* особенности WebView на Android и iOS;
* graceful degradation для слабых устройств.

## Рекомендуемый основной набор инструментов

## Стилизация

Предпочтительный порядок:

1. **Tailwind CSS** — если важна скорость сборки UI и высокая продуктивность.
2. **CSS Modules** — если нужен более строгий и контролируемый стиль.
3. **vanilla-extract** — если нужен typed styling без runtime overhead.

## Анимации

Предпочтительный порядок:

1. **CSS transitions / keyframes**
2. **Web Animations API**
3. **Motion для React** — только точечно и в легком режиме
4. **AutoAnimate** — для списков, аккордеонов, вставок и удалений

## UI-примитивы

* headless / primitives подход;
* брать только нужные части, а не тянуть огромные UI-комбайны;
* строить свои обертки и единый слой компонентов.

## Иконки

* использовать tree-shakable SVG icon set;
* избегать бесконтрольных импортов больших наборов.

## Стандарты разработки

## Анимации

Базовое правило:

**по умолчанию любая анимация делается через CSS на transform и opacity.**

Подключение animation library оправдано только если нужен один из следующих кейсов:

* сложные enter/exit анимации;
* coordinated animation нескольких элементов;
* gesture + spring physics;
* layout animation, которую неудобно делать вручную.

### Практический стандарт

* tap / press / hover / focus — CSS;
* skeleton / shimmer — CSS;
* page transitions — CSS или легкий Motion;
* list reordering / expand-collapse — AutoAnimate или FLIP-подход;
* complex hero animation — Motion или GSAP точечно;
* gesture-driven premium component — react-spring + gesture только если это действительно оправдано.

## Что лучше избегать

## Почти всегда плохие решения для Telegram Mini Apps

* тяжелые all-in-one UI libraries;
* styled-components / emotion как дефолтный путь;
* постоянные blur / backdrop-filter по всему интерфейсу;
* массовый Lottie;
* Rive “для красоты везде”;
* Canvas loop без жесткого контроля;
* Three.js / react-three-fiber для обычного UI;
* анимации через setState на каждом кадре;
* will-change “на всякий случай”;
* глобальные re-render chains через context/store.

## Красные флаги

Плохие решения обычно выглядят так:

* добавить новую библиотеку ради одной мелкой анимации;
* делать “премиальный” фон на WebGL;
* строить весь интерфейс на glassmorphism с blur;
* сначала навесить эффекты, а оптимизацию оставить “на потом”.

## Архитектурные принципы

### 1. Static-first

Интерфейс должен хорошо выглядеть еще до добавления движения:

* сильная типографика;
* хороший spacing;
* чистая визуальная иерархия;
* аккуратные тени;
* мягкие градиенты;
* форма кнопок и карточек;
* контраст и читаемость.

### 2. Motion is enhancement

Анимация — не основа интерфейса, а усилитель.

### 3. Cheap first

Сначала всегда проверяется самое дешевое решение:

* CSS;
* SVG;
* WAAPI;
* только потом animation library;
* затем Lottie / Rive / Canvas;
* WebGL — почти никогда.

### 4. Runtime budget is real

Каждый пакет, каждый blur, каждый анимированный слой расходует бюджет производительности.

### 5. Telegram-native adaptation

Интерфейс должен строиться с учетом:

* safe area;
* theme vars;
* viewport changes;
* keyboard behavior;
* bottom action zones;
* слабых Android-смартфонов.

## Практические правила

### Общее

* Всегда проектировать mobile-first.
* Всегда считать Telegram WebView основной средой выполнения.
* Всегда предпочитать дешевое визуальное решение дорогому.
* Всегда сначала предлагать вариант без тяжелых библиотек.

### При выборе технологий

* Для простых анимаций использовать CSS.
* Для программных микровзаимодействий использовать WAAPI.
* Motion подключать только там, где он реально окупается.
* AutoAnimate использовать для типовых list/layout transition кейсов.
* Lottie и Rive — только lazy и только точечно.
* WebGL не использовать без очень сильного обоснования.

### При реализации

* Анимировать только `transform` и `opacity`, если нет очень веской причины иначе.
* Не анимировать layout-свойства без крайней необходимости.
* Не запускать постоянные render-loop эффекты в фоне.
* Не связывать анимацию с частыми React re-render.
* Не злоупотреблять blur, shadow и backdrop-filter.
* Не размазывать animation logic по дереву компонентов.

### По стилям

* Не использовать runtime CSS-in-JS как дефолт.
* Хранить design tokens централизованно.
* Использовать CSS variables для темы.
* Поддерживать Telegram theme adaptation нативно.

### По производительности

* Проверять impact каждого нового пакета.
* Делать lazy load для дорогих частей.
* Использовать virtualization для длинных списков.
* Проверять анимации на слабом Android, а не только на десктопе.

## Как оценивать качество фронтенда

Хороший фронтенд должен давать такой результат.

### По UX

* интерфейс ощущается живым, но не дерганым;
* нажатия дают мгновенный отклик;
* экраны открываются без фризов;
* скролл остается легким.

### По технике

* минимум лишних зависимостей;
* нет тяжелых эффектов “для понта”;
* нет ререндер-штормов;
* анимации изолированы от React state;
* тяжелые части лениво подгружаются.

### По визуалу

* современный вид достигается композицией, а не дорогими эффектами;
* premium feeling создается за счет:

  * spacing;
  * hierarchy;
  * motion timing;
  * subtle highlight;
  * quality of states;
  * consistency.

### По архитектуре

* решение легко поддерживать;
* эффекты легко отключать;
* интерфейс легко упрощать для слабых устройств;
* весь проект не зависит от одной тяжелой библиотеки.

---

## Основная идея

Фронтенд Telegram Mini App должен выглядеть современно и дорого, но оставаться технически дешевым.

Максимум качества должен достигаться через:

* композицию;
* типографику;
* градиенты;
* аккуратные состояния;
* легкие transform/opacity-анимации.

Тяжелые технологии допустимы только как редкий акцент, а не как основа интерфейса.

---

## Главный принцип

**Максимум визуального ощущения за минимальную цену кадра.**

Практически это означает:

* сначала строить выразительность на статике;
* затем добавлять минимальную динамику на дешевых свойствах;
* любую дорогую технологию пропускать через вопрос: действительно ли этот эффект нельзя получить дешевле;
* все тяжелые эффекты делать точечными, ленивыми и отключаемыми;
* Telegram-native качество достигать не библиотеками, а корректной работой с темой, safe area и viewport.
