# PRD — Khujandi Mini App (MVP)

Версия: 1.2  
Дата: 2026-03-27  
Статус: Final (утверждено тимлидом)

## 1. Обзор продукта

Khujandi Mini App — Telegram Mini App для заказа готовой еды и доставки по городу.  
MVP покрывает полный операционный цикл:
- клиент оформляет и оплачивает заказ в Mini App;
- администратор назначает курьера;
- курьер ведет заказ по статусам;
- участники получают уведомления через Telegram-бота;
- после завершения заказа собираются отзывы (двусторонние).

## 2. Цели MVP

### 2.1 Продуктовые цели
- Запустить стабильный контур «заказ -> доставка -> завершение -> отзыв» внутри Telegram-экосистемы.
- Снизить ручную координацию в чатах за счет прозрачных статусов и обязательных уведомлений.
- Обеспечить управляемость операций через RBAC и отдельную веб-админку.

### 2.2 Операционные цели
- Обеспечить предсказуемую актуальность статусов через polling (SLA p95 <= 10 сек).
- Сделать критические события доставки наблюдаемыми в реальном времени через бота.
- Обеспечить безопасный доступ для Mini App и веб-админки по отдельным auth-контурам.

## 3. Не-цели (Out of Scope для MVP)

- Авто-назначение курьеров.
- Очереди/Redis и автоматические ретраи уведомлений.
- Продвинутая BI-аналитика и дашборды.
- Автоматический пересчет репутации/VIP.
- 2FA для веб-админки (после MVP).
- Отдельный онлайн-чардж за платное переименование магазина (в MVP ручной учет).

## 4. Контекст и ограничения

### 4.1 Технологический контекст
- Backend: NestJS + TypeScript + Prisma + PostgreSQL.
- Frontend: React + Vite + TypeScript.
- Архитектура: `layered monolith` + `vertical slices`.
- Telegram-бот: модуль внутри backend.
- Чтение изменений: polling `GET /events?since=<cursor>`.

### 4.1.1 Каноническая архитектурная модель

- `Layered architecture` задает правило внутренних зависимостей: `presentation -> application -> domain -> infrastructure`.
- `Vertical slice` является основной единицей поставки ценности, планирования, acceptance-сценариев и тестирования.
- В MVP используется capability-based slicing: слайс выделяется вокруг устойчивой продуктовой возможности (`capability`), а не вокруг технического модуля или сущности.
- Модульность допустима как способ упаковки слайсов и общих технических возможностей (`shared`), но не является главной архитектурной осью.

### 4.2 Базовые ограничения MVP
- Telegram WebApp auth обязателен для Mini App.
- RBAC обязателен для всех write-операций.
- Очереди и Redis не используются.
- Cursor/revision в API передаются строкой (BigInt).

## 5. Роли и доступ

### 5.1 Канонические роли в контрактах (API/DB/логика)
`boss`, `manager`, `admin`, `seller`, `courier`, `client`.

### 5.2 UI-лейблы
Бизнес-лейблы вида «худ*» используются только в интерфейсе и не используются в технических контрактах.

### 5.3 Краткая матрица ответственности
- `client`: витрина, checkout, просмотр статуса, отзыв о курьере.
- `courier`: прием назначенного заказа, смена статусов, отзыв о клиенте.
- `seller`: управление своими магазинами/товарами.
- `admin`: назначение курьеров, отмена заказа, операционный контроль.
- `manager`: управление клиентами/курьерами (по бизнес-правилам).
- `boss`: полный доступ + provisioning админ-аккаунтов веб-админки.

## 6. Scope MVP (In Scope)

1. Витрина магазинов и товаров (доступна до авторизации).
2. Онлайн-оплата заказа через локального провайдера.
3. Создание заказа только после успешной оплаты.
4. Ручное назначение курьера администратором.
5. Жизненный цикл заказа с историей статусов.
6. Polling событий через `/events`.
7. Telegram-бот:
   - новый заказ,
   - назначение курьера,
   - каждая смена статуса,
   - негативный отзыв.
8. Двусторонние отзывы:
   - клиентский отзыв через Telegram-бота (3 шага),
   - отзыв курьера о клиенте.
9. Отдельная веб-админка.
10. Soft-delete и аудит критических действий.

### 6.1 Канонические capability slices MVP

1. `catalog` — витрина магазинов и товаров.
2. `checkout-payment` — checkout и создание заказа только после успешной оплаты.
3. `delivery-assignment` — назначение курьера администратором.
4. `delivery-tracking` — переходы статусов, история и polling обновлений.
5. `order-cancellation` — операционная отмена и ручной refund workflow.
6. `reviews-feedback` — двусторонние отзывы и негативные алерты.
7. `admin-access` — отдельный login/password контур веб-админки.

## 7. Ключевые бизнес-решения (фиксировано)

1. **Оплата в MVP**: онлайн-оплата через локального провайдера.
2. **Условие создания заказа**: заказ создается только после подтвержденной успешной оплаты.
3. **Ошибка или таймаут оплаты**: заказ не создается; клиент получает ошибку и возможность повторить оплату.
4. **Отмена клиентом**: невозможна.
5. **Кто может отменять**: `admin`, а также `courier` в операционном кейсе отсутствия заказа/товара в магазине.
6. **Возврат средств при отмене**: ручной оператором (не автоматический refund в MVP).
7. **Успешный заказ для KPI**: только `COMPLETED`.
8. **Polling SLA MVP**: p95 <= 10 секунд.
9. **Уведомления Telegram-бота**: все 4 типа обязательны (must-have).
10. **Авторизация веб-админки**: отдельный логин/пароль, без self-signup, provisioning только ролью `boss`.
11. **2FA**: не используется в MVP.
12. **Политика пароля админки**: минимум 12 символов.
13. **Защита логина админки**: 5 неудачных попыток за 15 минут -> блокировка 30 минут + аудит.
14. **Сессии админки**:
    - access token: 15 минут;
    - refresh/session lifetime: 3 дня;
    - auto-logout: 30 минут неактивности.
15. **Отзывы**: двусторонние в MVP; клиентский отзыв через бота:
    `rating(1-5) -> reason_code(enum) -> comment(optional)`.
16. **Переименование магазина**: после 1 бесплатной попытки — платно, учет платности вручную (без отдельного online charge).

## 8. Пользовательские потоки (MVP)

Пользовательские потоки ниже являются acceptance-сценариями для capability slices MVP.

### UF-01: Клиент оформляет и оплачивает заказ
1. Клиент открывает Mini App и выбирает товары.
2. При checkout проходит Telegram auth (если не авторизован).
3. Инициируется онлайн-оплата у локального провайдера.
4. При успешной оплате создается заказ со статусом `CREATED`.
5. Бот отправляет уведомление о новом заказе администраторам.
6. При ошибке/таймауте оплаты заказ не создается, клиент видит ошибку и кнопку повторной оплаты.

### UF-02: Администратор назначает курьера
1. Админ получает событие о новом заказе.
2. Выбирает курьера и назначает на заказ.
3. Заказ переходит в `ASSIGNED`.
4. Бот отправляет уведомление назначенному курьеру.

### UF-03: Курьер ведет доставку
1. Курьер подтверждает принятие заказа.
2. Меняет статусы: `ASSIGNED -> IN_PROGRESS -> DELIVERED -> COMPLETED`.
3. Каждый переход пишется в `order_status_history` и в `events`.
4. Клиент, админка и связанные интерфейсы получают обновления через polling.

### UF-04: Отмена заказа (операционная)
1. Отмена инициируется `admin` или `courier` (по разрешенному кейсу).
2. Заказ переводится в один из статусов отмены с причиной.
3. Возврат средств инициируется вручную оператором.
4. Событие отмены и действие по возврату логируются.

### UF-05: Отзывы после завершения
1. После `COMPLETED` запускается двусторонний сбор отзывов.
2. Клиент оставляет отзыв через Telegram-бота (3 шага).
3. Курьер оставляет отзыв о клиенте (в интерфейсе курьера по согласованному каналу).
4. При `rating <= 2` формируется негативный алерт админам через бота.

### 8.1 Трассировка пользовательских потоков к slices

| Flow | Основной slice | Дополнительные slices |
|------|----------------|-----------------------|
| `UF-01` | `checkout-payment` | `catalog` |
| `UF-02` | `delivery-assignment` | `delivery-tracking` |
| `UF-03` | `delivery-tracking` | `delivery-assignment` |
| `UF-04` | `order-cancellation` | `delivery-tracking` |
| `UF-05` | `reviews-feedback` | `delivery-tracking` |

## 9. Жизненный цикл заказа

### 9.1 Основные статусы
`CREATED -> ASSIGNED -> IN_PROGRESS -> DELIVERED -> COMPLETED`

### 9.2 Статусы отмены
- `CANCELLED_BY_ADMIN`
- `CANCELLED_BY_COURIER_UNAVAILABLE` (операционный кейс отсутствия заказа/товара в магазине)

### 9.3 Правила переходов
- Переходы валидируются сервером (state machine).
- Невалидный переход -> `409 CONFLICT`.
- Любой валидный переход порождает запись в `order_status_history` и `events`.

## 10. Функциональные требования

### 10.1 Каталог и магазины
- CRUD магазинов и товаров с soft-delete.
- Витрина доступна без авторизации.
- Продавец управляет только своими сущностями.
- Переименование магазина:
  - 1 бесплатная попытка;
  - далее платно (ручной учет в MVP);
  - `shop_name` в существующих заказах не изменяется (snapshot).

### 10.2 Заказы и оплата
- Checkout с онлайн-оплатой через локального провайдера.
- Заказ создается только после успешной оплаты.
- При ошибке/таймауте оплаты заказ не создается, доступен retry.
- Назначение курьера выполняет админ.
- Отмена доступна только `admin`/`courier` (по правилам), клиент не отменяет.

### 10.3 Отзывы
- Двусторонние отзывы в MVP.
- Клиентский отзыв через Telegram-бота:
  - `rating` (1..5),
  - `reason_code` (enum),
  - `comment` (optional).
- Негативный отзыв (`<=2`) -> обязательный алерт админам через Telegram-бота.

### 10.4 Авторизация и RBAC
- Mini App: `POST /auth/telegram`, проверка `initData` на backend, выдача JWT.
- `initDataUnsafe` не используется для доверенных решений.
- Веб-админка: отдельный login/password auth-контур.
- Админ-аккаунты только через provisioning ролью `boss`, без self-signup.
- RBAC обязателен для всех операций изменения.

### 10.5 События и polling
- Любое доменное изменение создает событие.
- Чтение: `GET /events?since=<cursor>`.
- Формат событий стабилен для будущего перехода на SSE/WS.
- `revision`/`cursor` возвращаются строкой.

### 10.6 Telegram-бот (must-have уведомления)
Обязательные типы:
1. Новый заказ.
2. Назначение курьера.
3. Каждая смена статуса.
4. Негативный отзыв.

## 11. Нефункциональные требования

### 11.1 Performance и SLA
- Polling SLA MVP: p95 задержка отображения обновлений <= 10 секунд.
- Ключевые API должны обеспечивать стабильный отклик под целевой MVP-нагрузкой.

### 11.2 Security
- Mini App auth: строгая серверная валидация Telegram `initData` + `auth_date`.
- Веб-админка:
  - пароль >= 12 символов;
  - без 2FA в MVP;
  - rate-limit и временная блокировка;
  - аудит входов.
- Политика блокировки:
  - 5 неудачных попыток за 15 минут;
  - блокировка на 30 минут;
  - обязательная запись события в аудит.

### 11.3 Session management (веб-админка)
- Access token: 15 минут.
- Refresh/session lifetime: 3 дня.
- Auto-logout: 30 минут неактивности.

### 11.4 Observability
- Единый формат ошибок: `{ error: { code, message, details }, trace_id }`.
- Аудит:
  - входы/неудачные попытки/блокировки;
  - операции изменения статуса;
  - отмены и действия по возвратам;
  - критичные уведомления Telegram-бота.

## 12. Метрики успеха MVP

### 12.1 Продуктовые
- `KPI-01`: Конверсия `order_created -> COMPLETED`.
- `KPI-02`: Среднее время `order_created -> ASSIGNED`.
- `KPI-03`: Доля негативных отзывов (`rating <= 2`).
- `KPI-04`: Время реакции админа на негативный отзыв.

### 12.2 Технические
- `KPI-T-01`: p95 lag по polling <= 10 секунд.
- `KPI-T-02`: Доля 5xx на критичных endpoint.
- `KPI-T-03`: Доставка 4 обязательных типов уведомлений Telegram-бота.

## 13. Риски и меры снижения

1. **Рост нагрузки из-за polling**  
   Меры: cursor-based инкрементальная выдача, оптимизация payload, лимиты частоты опроса.

2. **Сбои платежного провайдера**  
   Меры: заказ не создается до успешной оплаты, retry UX, мониторинг payment errors/timeouts.

3. **Ручные возвраты при отмене**  
   Меры: операционный регламент, обязательный аудит, контроль времени обработки возврата.

4. **Недоставка уведомлений Telegram-бота**  
   Меры: мониторинг отправки, логирование ошибок, ручной fallback процесс для операторов.

5. **Компрометация админ-аккаунтов**  
   Меры: парольная политика, rate-limit, блокировки, аудит входов, короткий access token.

## 14. Этапы реализации (релизный план)

### M1 — Core checkout + payment
- `catalog`.
- `checkout-payment`.
- Интеграция локального платежного провайдера.
- Ошибки оплаты и retry.

### M2 — Delivery operations
- `delivery-assignment`.
- `delivery-tracking`.
- `order-cancellation`.
- Polling events + SLA контроль.
- 3 уведомления Telegram-бота (новый заказ, назначение, смены статусов).

### M3 — Веб-админка + усиление безопасности
- `admin-access`.
- Отдельная веб-админка.
- Login/password auth, provisioning через `boss`.
- Политики сессий, rate-limit, блокировки, аудит входов.

### M4 — Reviews + negative alerts + go-live
- `reviews-feedback`.
- Клиентский 3-шаговый отзыв через бота.
- Негативные алерты (4-й обязательный тип уведомлений).
- Финальная регрессионная и smoke-проверка по slices с последующим запуском.

## 15. Критерии готовности к запуску (Go-Live Gate)

- Все ключевые пользовательские потоки (`UF-01..UF-05`) проходят end-to-end.
- Каждый capability slice MVP имеет acceptance-сценарий и минимальный e2e-контур.
- Платежный контур стабилен: заказ создается только после успешной оплаты.
- RBAC и state machine валидируют права и переходы без обходов.
- Polling SLA p95 <= 10 секунд подтвержден на тестовой нагрузке.
- 4 обязательных уведомления Telegram-бота работают и наблюдаемы.
- Веб-админка соответствует параметрам безопасности MVP.
- Аудит критичных событий включен.
- Нет открытых P0-блокеров.
